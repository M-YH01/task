# 8번 과제 제출문 — 소개 페이지에 패스키(WebAuthn) 비공개 자리 붙이기

- 공개 결과물 주소: `https://(여기에 본인 주소 한 개)`  ← 열면 첫 화면이 1번 소개 페이지이고, 로그인·가입 없이 열립니다.
- 소스 주소: `https://github.com/(본인 계정)/(저장소)/tree/main/task8`  ← 서버·화면·테스트가 모두 `task8` 폴더에 있습니다.
- 내용 안내: 이 제출물에 들어 있는 이름·계정(가온, 나래)·비공개 자료는 모두 **지어낸 예시**이며 실제 개인정보가 아닙니다. 서버 비밀값(설정 코드 등)은 어떤 파일에도 저장하지 않았습니다.

## 인증 구현 설명서

### ① 무엇으로 붙였나
- **직접 구현**했습니다. 인증 서비스(Auth0, Firebase 등)나 WebAuthn 라이브러리는 쓰지 않았습니다.
- 서버: Python 표준 라이브러리만 사용한 `task8/server.py` 한 파일(CBOR 해석, ES256 서명 검증, 세션 포함). 화면: `intro.html`(공개), `private.html`(비공개 자리·확인 버튼).
- 브라우저는 표준 WebAuthn API(`navigator.credentials.create/get`)를 쓰고, 서버가 서명을 직접 검증합니다. 서명 검증 함수는 외부 암호 라이브러리 `cryptography`와 같은 답을 내는지 테스트(`test_all.py`)로 맞춰 보았습니다.
- 1번 소개 페이지는 내용 그대로 `/`(공개)에 두고, 비공개 자리는 별도 화면 `/private`로 붙였습니다.

### ② 왜 그걸 골랐나
- 이번 과제의 핵심이 "공개키만 서버에 두고, 서명을 서버가 직접 확인하는 것"이라, 그 과정을 눈으로 확인하고 설명할 수 있도록 직접 구현을 택했습니다. 서비스에 맡기면 기록으로 보이지 않는 부분이 생깁니다.
- 처음에는 claude.ai 아티팩트에 붙이려 했지만, 아티팩트 안에서는 브라우저가 패스키 사용을 막아 등록이 되지 않았습니다(`NotAllowedError … publickey-credentials-create … not enabled`). 그래서 `localhost`(WebAuthn이 안전한 곳으로 인정)에서 도는 작은 서버로 바꿨습니다.
- 계정 두 개를 나눈 이유는 "남의 패스키·남의 자료로 열리지 않는다"를 실제 요청으로 보여 주기 위해서입니다.

### ③ 어디를 어떻게 고쳤나 (`task8/server.py` 기준 줄 번호)
| 흐름 | 지나가는 곳 | 하는 일 |
|---|---|---|
| 등록 | 654(`/api/challenge`) → 702(`/api/register`) | 서버가 계정별 등록 질문(120초·1회용) 발급 → attestationObject에서 **공개키만** 꺼내 `credentials.json`에 저장(계정 번호 `accountId` 함께). 이미 패스키가 있는 계정은 그 계정으로 로그인한 세션만 추가 가능 |
| 로그인 | 801(`/api/login/challenge`) → 822(`/api/login/verify`) | 로그인할 때마다 새 질문(120초·1회용). 861 등록 안 된/삭제된 패스키 거절, **866 질문을 받은 계정의 패스키가 아니면 거절**, 이후 380(`ecdsa_p256_verify`)로 서명 검증, 통과해야 427(`new_session`)로 세션 발급 |
| 비공개 자료 조회 | 599(GET `/api/private`)·940(POST), 513(`_private_for_session`), 609→530(`_other_account_private`) | 세션에 적힌 계정의 자료만 반환. 주소의 `?account=`·본문의 `accountId`는 무시. 주소에 남의 계정 번호를 직접 쓰면 530에서 **403** |
| 로그아웃 | 1000(`/api/logout`) | 서버의 세션을 지움 → 같은 토큰은 401 |
| (참고) 패스키 삭제 | 951 | 내 계정 패스키만 삭제(남의 것은 971 부근에서 403), 지운 패스키로 연 세션도 끊음 |

세션은 32바이트 난수 토큰이며 서버에는 SHA-256 해시만 저장(445 `lookup_session`). 비밀번호 입력칸은 어디에도 없습니다.

### ④ 안 열리는 것을 확인한 기록 (통과한 요청 ↔ 거절된 요청)
원본: `task8/evidence_checks.jsonl`, `task8/request_log.jsonl`. 세션 토큰은 앞 4글자만 보이게 가렸습니다.

**확인 1 — 로그인 없이 열기**

| 통과한 요청 | 거절된 요청 |
|---|---|
| `GET /api/private` + 가온 세션 → **200**, 자료 3건 | `GET /api/private` (토큰 없음) → **401** `unauthorized` |
| `GET /api/private` + 나래 세션 → **200**, 자료 4건 | `GET /api/private` + 엉터리 토큰 → **401** |
| | `GET /api/accounts/a2/private` (토큰 없음) → **401** |

**확인 2 — 남의 패스키·남의 세션으로 열기 (계정 두 개 서로 맞교환)**

| 통과한 요청 | 거절된 요청 |
|---|---|
| 가온 세션으로 가온 자료 주소 → **200** | 나래용 질문에 **가온의 패스키 서명**으로 로그인 → **401** `credential_not_for_this_account` |
| 나래 세션으로 나래 자료 주소 → **200** | 가온용 질문에 **나래의 패스키 서명**으로 로그인 → **401** `credential_not_for_this_account` |
| | 가온 세션으로 `GET /api/accounts/a2/private` → **403** `forbidden_other_account` (나래 자료 개수 거절 전 4 → 후 4) |
| | 나래 세션으로 `GET /api/accounts/a1/private` → **403** (가온 자료 개수 전 3 → 후 3) |
| | 가온 세션으로 나래의 패스키 삭제 요청 → **403** (나래 패스키 수 전 1 → 후 1) |

- 거절 전후 개수가 같다는 점: 서버 기록(`cross_account_denied`)에 `targetCountBefore`와 `targetCountAfter`가 같은 값으로 남았고(4/4, 3/3), 화면에서도 거절 전후 가온 3→3, 나래 4→4가 같았습니다.
- 주소·본문에 다른 계정을 적은 요청: 가온 세션으로 `GET /api/private?account=a2` → **200이지만 가온(a1) 자료 3건만**, `POST /api/private {"accountId":"a2"}` → **200, 가온 자료 3건만**. 가온 세션으로 나래 계정에 패스키 추가 질문(`POST /api/challenge {"accountId":"a2"}`) → **403**.

**확인 3 — 이미 쓴 질문 재사용**

| 통과한 요청 | 거절된 요청 |
|---|---|
| 새 질문으로 가온 로그인 → **200**, 세션 발급 | 같은 질문·같은 서명을 그대로 다시 보냄 → **401** `challenge_already_used` |

**확인 4 — 패스키 삭제 뒤 로그인 (나래, 마지막 패스키)**

| 통과한 요청 | 거절된 요청 |
|---|---|
| 삭제 전, 그 패스키로 연 세션으로 자료 요청 → **200** | 삭제 뒤, 같은 옛 세션으로 자료 요청 → **401** |
| `POST /api/credentials/delete` → **200** (`remaining 0`, 세션 2개 끊김) | 삭제 뒤 새 로그인 질문 요청 → **400** `no_credentials_registered` |
| | 삭제 전에 받아 둔 서명으로 지운 패스키 로그인 → **401** `unknown_credential` |

(참고: 마지막 패스키를 지우면 서버가 로그인 질문 자체를 만들지 않아서, "지운 패스키로 로그인" 요청은 삭제 전에 받아 둔 서명으로 보냈습니다. 패스키가 둘 이상인 계정에서 하나를 지운 경우도 `test_all.py`와 카드 4 기록에서 `unknown_credential` 401을 확인했습니다.)

### ⑤ AI와 나
- AI(Claude)가 서버·화면 코드와 테스트를 작성했고, 저는 실행하면서 막히는 곳(패스키 등록 실패, 가상 인증기 설정, 깃 올리기)을 알려 주고 방향을 정했습니다.
- AI가 쓴 자체 테스트(`test_all.py`, 가짜 키 사용)는 "서버 코드가 맞게 판정하는지"만 보여 줍니다. 실제 브라우저에서 두 계정으로 돌린 결과(④의 기록)는 제가 직접 화면에서 실행해서 나온 것입니다.
- 아티팩트에서는 패스키가 막힌다는 사실과 그 대안(로컬 서버)은 AI가 먼저 알려 주었고, 제가 로컬 서버로 가는 데 동의했습니다.

### ⑥ 아직 못 막은 것
1. **설정 코드가 열쇠 역할**: 패스키가 0개인 계정은 서버 콘솔의 설정 코드만 있으면 새 패스키를 등록해 계정을 차지할 수 있습니다. 이메일·전화 같은 복구 수단이 없어서, 마지막 패스키를 지우면 이 방법밖에 없습니다.
2. **질문(challenge) 보관**: 로그인·등록 질문은 120초가 지나면 거절하지만, 기록은 파일에 최대 200개가 찰 때까지 남아 있고 시간이 지났다고 지우지는 않습니다.
3. **세션 토큰이 페이지 메모리에 있음**: 쿠키(HttpOnly)가 아니라 자바스크립트 변수에 있어서, 페이지에 악성 스크립트가 들어오면(XSS) 훔칠 수 있습니다.
4. **시도 횟수 제한이 설정 코드에만 있음**: 로그인 질문 요청 등은 횟수 제한이 없습니다.
5. **가상 인증기로 확인했고 attestation 검증 안 함**: 실제 기기(Windows Hello, 보안 키, 휴대폰)로는 확인하지 못했고, 기기 종류를 증명하는 attestation은 검증하지 않습니다(fmt `none`만 받음).
6. **패스키 영역은 공개 HTTPS 주소에서 동작하지 않음**: 공개 주소는 소개 페이지만 열리고, 패스키 영역은 서버를 켠 컴퓨터의 `http://localhost:8787/private`에서만 동작합니다.
7. **상대 계정이 있다는 사실·패스키 개수는 공개**: `/api/status`가 계정 이름과 패스키 개수를 로그인 없이 보여 줍니다.
8. 같은 계정이 로그인한 다른 기기의 세션을 한 번에 끊는 기능은 없습니다(패스키 삭제 시에만 끊김).

## 짧은 확인 방법

**① 어디로 가나요**
공개 소개: 위 공개 결과물 주소(로그인 없이 열림). 비공개 자리: 서버를 켠 컴퓨터에서 `http://localhost:8787/private` (공개 주소에서는 열리지 않습니다).

**② 세 단계 안에 무엇을 하나요**
1. `python server.py`를 켜고, 브라우저에서 `/private`을 열어 아무 로그인 없이 `http://localhost:8787/api/private`도 열어 봅니다.
2. 계정(가온·나래)에 각각 패스키를 등록합니다(처음 한 번, 서버 콘솔의 설정 코드 필요).
3. "전체 확인 실행"을 누릅니다.

**③ 무엇이 보이면 통과인가요**
`/api/private`을 로그인 없이 열면 401이 보이고, "전체 확인 실행" 뒤에 통과한 요청(200)과 막힌 요청(401/403)이 좌우로 나란히 나오며, "가온 3→3 / 나래 4→4 (둘 다 같음)"이 보이면 통과입니다.

**④ 안 될 때는 무엇이 보이나요**
- 붉은 상자 "NotAllowedError": 패스키가 든 인증기(DevTools 가상 인증기)가 꺼졌거나 페이지 포커스가 빠진 것 → 인증기를 켜고 페이지를 새로고침한 뒤 다시 실행합니다.
- 패스키 등록 시 "설정 코드 필요": 서버 콘솔의 코드를 입력합니다.
- 공개 주소에서 `/private`을 열면 열리지 않습니다(위 ⑥-6).
